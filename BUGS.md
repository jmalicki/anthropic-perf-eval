# Known bugs and limitations

## Open

- [ ] **The greedy's live-word counter does not see the two-op multiply-add select** – A SelectChoice without a precomputed delta, placed on the vector ALU (the two-op form: SUB at its cycle into `sub_temp`, multiply_add at cycle + 1 writing the dest), is invisible to the counter and to its agreement check. The check's intervals take `select_fma_ops` from `trace.fma_selects`, which records only delta-form selects (`ssa_greedy/mod.rs`, the `trace.fma_selects.insert` sites in the normal and force-schedule paths, and `compare_counter_with_intervals`), while address assignment gives the two-op form a dest from cycle + 1, an 8-word `sub_temp` and its reads held to cycle + 1 (`address_assign.rs`, `dest_write_interval`, `aux_defs`, `use_cycles`): up to 24 words per select the counter does not count. Reachable with `--select-choice fma` when CP-SAT follows, or with the select-choice hint pass plus fixed choices, on the standard emission. Address assignment still enforces the budget (an over-budget kernel fails, it is not emitted wrong). **Fix direction:** record every multiply-add SelectChoice the greedy places (both forms) in the set the check uses, and count `sub_temp` and the cycle + 1 dest in the counter; a test comparing counter and intervals with two-op selects.

- [ ] **`holds_reads` is wider than the selects the check models** – `ssa_greedy/mod.rs` (`let holds_reads = engine == Engine::Valu && opcode == SelectChoice`) holds the reads of every SelectChoice placed on the vector ALU to cycle + 1, including the two-op form above, but the agreement check models only the delta form (`fma_selects`). For the two-op form the counter then holds its reads but still misses its writes. Fold into the fix above: one set, used by the counter and the check.

- [ ] **Flaky: `test_ssa_cpsat_shifted_live_out_starts_at_first_lane`** – Failed once in CI (PR #74, run 45461775694 attempt 1; passed on rerun) at `assert_eq!(solution.is_some(), budget == 16)`: `left: false, right: true`, i.e. the 16-word solve returned no solution. The test gives CP-SAT a 5 s wall-clock limit and no deterministic-time budget, in a debug build on a shared runner, so under load the solve can stop before its first solution. Likely fix: a `cpsat_deterministic_time` budget (and a generous wall-clock backstop), or hints that make the first solution immediate.

- [ ] **Emission-declared symmetry rows are not justified by a symmetry** – `sym_ord_*` chains every op of one `(round, iter, tree level)` ordering group by its greedy cycle, and `sym_lex_*` orders the first op of each vector group, once per `(round, iter)` stream. A row `cycle[i] <= cycle[j]` is valid only if some automorphism of the model maps one schedule to another that satisfies it; for vector groups that is a swap of two structurally identical groups, and a set of such swaps can order **one** anchor per group. Measured with `--cpsat-symmetry-rows checked` (which classifies the declared pairs against the group orbits found by `cpsat_scheduler/group_symmetry.rs`): at 4x64 and 6x64, of 53 declared pairs 6 are justified by a group swap, 28 order two ops of the same group, and 19 involve groups that are not identical or ops outside groups; the lex streams add one anchor per round, i.e. several anchors per group. `verification/group_symmetry.py` (GS2, GS3) shows that both patterns can raise the optimum on small instances. Not observed on the kernel: solved to optimality without the greedy cap (`--cpsat-objective makespan --cpsat-greedy-alap-slack none --asap-alap-tightening simple`), 4x8 (74), 4x16 (75) and 5x8 (93) give the same optimum with and without the declared rows (2 and 3 rounds have none). The declared ordering also drives symmetry-aware ASAP tightening (`tighten_asap_by_symmetry_ordering`). **Workaround / fix:** `--cpsat-symmetry-rows checked` (only justified rows, domains of corresponding ops made equal, declared ordering not used for tightening) or `none` to drop the explicit rows while retaining the declared ordering during energetic ASAP tightening. The default remains `declared`.

- [ ] **Per-section CP-SAT scratch intervals use the issue cycle of shifted ops** – Found while moving every time in the model to `cpsat_scheduler/op_times.rs` (not fixed there: that change keeps the model byte-identical). In segment mode (per-section feasibility solves), a live-in value's interval ends at its last reader's issue cycle + 1 and a live-out value's interval starts at its definer's issue cycle. The issue cycle of a shifted op is free (only bounded by precedence and by its completion cycle), so a shifted reader's lanes can read after the interval ends and a shifted definer's lanes can write before it starts; the same applies to a select reader on the multiply-add path (reads at issue + 1). `segment_end` is likewise only bounded by issue cycles. The full-kernel model is not affected (it uses `last_read_end` and `first_write`), and `verify_scratch_budget_all_readers` does not run in segment mode, so nothing checks it. **Fix direction:** use `OpTimes::last_read_end` / `first_write` for these intervals and `finish_alternatives` for `segment_end` (a model change; measure it).

- [ ] **"Stopped on the wall-clock limit" warning misses a wall-clock stop** – The warning in `cpsat_scheduler/model.rs` fires only when `response.wall_time` reached the time limit **and** `response.deterministic_time < budget`. Observed with `--cpsat-deterministic-time 60` at 16 rounds: one run reported `deterministic_time` 408 and ended at 5,410 s; another reported 402 and ended at 21,628 s against a 21,600 s limit. Both reported values exceed the budget, so no warning fired for the second run, whose result depended on load (`scripts/run_cpsat_ablation.py` treats runs with this warning as invalid, so it would also accept such a run). Why the reported value exceeds the budget it was given (`params.max_deterministic_time`) is not established here; the field comes from the pinned `cp_sat` dependency. **Fix direction:** use the solver's own stop reason if the response exposes one. A wall-time threshold alone is not enough: a solve that ends just before the limit would be misreported.

- **`compute_live_intervals` gives an untouched vector group a [0, 1] interval** – A group none of whose VRegs is written by a scheduled op (its producer was a skipped dead store) still gets an 8-word interval at cycle 0 (`unwrap_or(0)` in the group pass of `address_assign.rs`). Kernels are DCE'd before scheduling, so this has only been seen on random test programs; the greedy agreement check filters such groups out. **Fix direction:** skip groups with no write and no read.

- **Greedy policy inputs still count freed words per operand** – `build_inflation_candidate` and the sort candidates compute `words_freed` and LUC from `srcs` only, so they miss `keep_live` and vector-group aliases and count `x + x` twice. The budget check and the counter itself are exact (T16); these are ordering heuristics only.

- **T7 counterexample: slot tightening excludes a feasible schedule** – Theorem T7 in [docs/LIVENESS_SPECIFICATION.md](docs/LIVENESS_SPECIFICATION.md) claimed that slot-aware ASAP/ALAP tightening "only removes infeasible regions" so the tightened bounds still contain at least one feasible schedule. **Spec bug:** That claim is false for composition (multiple steps + precedence fixpoint); Z3 counterexample T7-two-step shows two valid one-step exclusions can remove all feasible schedules. **Behavioral bug:** 2r/16b with tightening → 368-cycle schedule (295 empty cycles); same config without tightening → 36-cycle **valid** schedule, so a feasible schedule exists but is excluded or the solver finds a bad one. **Z3 proof of error:** T7-strong-guarantee-fails-asap-only (`uv run python -m verification.verify -t T7-strong-guarantee-fails-asap-only`) returns **SAT**: there exists a feasible schedule (e.g. (0,1,2)) that the ASAP-only exclusions remove. So the SAT result **proves an over-tightening error** in ASAP/ALAP tightening (we exclude at least one feasible schedule; strong guarantee violated). **Z3:** One-step lemma proven; composition not; strong guarantee proven for entailed exclusions only; attempt for ASAP-only fails (result preserved). **Workaround:** Use `--no-enable-asap-alap-tightening`. **Fix direction:** Tightening or fixpoint logic must be changed so we still tighten beyond greedy but composition preserves at least one feasible schedule (greedy-cap would contradict the goal). See [docs/SLOT_TIGHTENING_T7_COUNTEREXAMPLE.md](docs/SLOT_TIGHTENING_T7_COUNTEREXAMPLE.md) § "What we actually need".

- **CP-SAT presolve INFEASIBLE on SelectChoice toy tests (no greedy hints)** – Seven tests in `cpsat_scheduler::tests::ssa_tests` fail with CP-SAT status INFEASIBLE during presolve: "empty domain after intersecting with [0]" on a cumulative constraint (Flow capacity 1 with optional intervals). **Root cause (found):** `enable_asap_alap_tightening: true` (default). Investigation test `test_investigate_valu_shift_toy_presolve_infeasible` shows that only the variant with `enable_asap_alap_tightening: false` passes; baseline, no default hint, default machine, and ForceFma all still fail. So ASAP/ALAP tightening over-constrains for these small programs and triggers presolve INFEASIBLE. **Workaround:** Use `enable_asap_alap_tightening: false` when running CP-SAT on small/toy models without greedy hints; or mark tests `#[ignore]`. See `docs/CP_SAT_PRESOLVE_INFEASIBLE_ANALYSIS.md`.

- **Validation failure: hash value used as offset in idx computation (kernel_to_validate.json, 4r/256)** – Traced with `scripts/debug_validation_trace.py` and `scripts/trace_group20.py`. All 256 batch indices wrong. **Cycle 985:** `vstore` writes final-round hash values to scratch 10–17 (group 0’s value output). **Cycle 986:** `multiply_add(49, 49, 27, 10)` computes `idx = idx*2 + offset`; the “offset” operand is read from scratch 10–17. Those locations were just overwritten at 985 with the **hash**, so the multiply_add uses the hash value as offset instead of the wrapped 0/1. Result: wrong indices (e.g. got 56 vs ref 27) and wrong values. **Likely cause:** Scratch allocation or scheduling reuses the same registers for (1) round output value and (2) offset input to next idx, and the store at 985 overwrites the offset before the multiply_add at 986 reads it (or the dependency graph allows the wrong ordering). **Repro:** Run validation on `kernel_to_validate.json` with `--rounds 4 --batch-size 256`; trace with `uv run python -m scripts.debug_validation_trace --kernel kernel_to_validate.json --rounds 4 --batch-size 256` and `uv run python -m scripts.trace_group20 --kernel kernel_to_validate.json --rounds 4 --batch-size 256 --group 0`. **Note:** Run trace scripts as `python -m scripts.<script>` from project root to avoid `scripts/bisect.py` shadowing stdlib `bisect`.

So one of these intervals was wrong: (1) the hash value’s interval end was &lt; 986 (value not extended to vstore’s cycle), or (2) the offset’s interval end was &lt; 984 (offset not extended to multiply_add’s cycle). Liveness is extended from each op’s `srcs` to that op’s cycle; vstore has `srcs = [addr, src]`, multiply_add has `srcs = [idx, v_2, offset]`. **Next steps:** Re-run with `SCHEDULER_DEBUG=1` and `--output-json`, inspect stderr for `[DEBUG compute_live_intervals]` vstore and confirm value VReg extended to vstore cycle; in scheduler JSON use `vreg_to_addr` to find VRegs at address 10 and check `vregs` intervals for overlap; add unit test: value at T, vstore at T+1, offset at T−1, multiply_add at T+2 → assert value and offset get different addresses.

## Fixed

- [x] **The scheduler JSON varied between runs of the same build** – Seen while comparing scheduler JSONs for PR #79 (`ops[].writes` order). Hash-ordered output: `Op::reads`, `Op::writes` and `Op::dep_ids` are `HashSet`s and were written in iteration order (`write_ssa_schedule_json`, `schedule_output.rs`); `liveness_curve[].becoming_live` / `dying` (events sorted by cycle only, ties in `HashMap` order); object keys of every `HashMap` field; `valu_shift_debug.samples` (the first ten of each kind from a `HashMap` iteration over `shifted_alu_cycles`, so different ops each run whenever lanes are shifted); and the ordering rows of `schedule_constraints` (`groups.values()` / `streams.values()`, `schedule_constraints.rs`). **Fix:** the sets are written sorted, liveness events are tie-broken by VReg, the JSON goes through `serde_json::Value` (sorted keys), samples are taken in op id order, and ordering groups and streams are `BTreeMap`s. **Verified** byte-identical over two runs each: greedy 2 rounds / batch 256 (before: 31,837 differing values); greedy 3 rounds / batch 64 with `--greedy-split-shift` (wavefront); CP-SAT 3 rounds / batch 64 with `--cpsat-split-shift-hint`, deterministic time 0.5 (writes `schedule_constraints`). Not verified for other options (e.g. window probe reports, relaxed scratch). Test: `tests/test_determinism.py::test_scheduler_json_is_reproducible` (the two 3-round builds).

- [x] **DCE left ConstChoice ALU alternatives that name a constant it removed** – Found by the index-transform parity test of PR #77. `eliminate_ssa_dead_code` dropped dead constants but kept the other `ConstChoice`s' ALU derivations (`Add { a_value, b_value }`, ...) that read them. Not only under `--values-only` with the mirrored index (6 = 1 + 5 and 9 = 4 + 5 once the header-word-5 pointer load and its address constant 5 die): every emission measured had some, e.g. 8 = 1 + 7 and 9 = 2 + 7 at batch 256, 9 = 1 + 8 at batch 8. The CP-SAT model resolved a missing operand to the constant itself (`value_to_producer_idx.get(..).unwrap_or(&idx)`, `cpsat_scheduler/model.rs`), giving `cycle >= cycle + 1` under the alternative's literal: the alternative could never be chosen, even where it would save a cycle (shown by the test below), so no kernel or accounting was wrong; the model only carried dead literals and the scheduler JSON's `const_alu_derivable` could be true for a constant with no usable derivation. **Fix:** DCE drops alternatives whose operands no kept op produces (`drop_alternatives_without_producer`, `kernel_builder/emit_ssa.rs`); the model returns an error for such an alternative in a whole-kernel solve, and in a section solve (operand produced in an earlier section) switches it off with an explicit row instead of the self-precedence. Greedy kernels are unchanged (the greedy never reads the alternatives); CP-SAT models change wherever an alternative was dropped, which includes default builds. Tests: `test_dce_drops_const_alternatives_reading_a_removed_constant`, `test_dce_keeps_no_const_alternative_without_producer` (emissions at 2/16 rounds, batch 8/256), `test_const_choice_alternative_without_producer` and its control `test_const_choice_alu_derivation_with_live_operands_is_chosen`. The hardware zero is the one operand with no producer that is not stale: with a reserved zero VReg the emitter lists e.g. `-n = 0 - n`; DCE keeps it and the model switches it off (the derivation names operands by producer op id, so it cannot be chosen; it never could), tested by `test_const_choice_zero_operand_is_kept_and_switched_off`. `test_whole_kernel_model_and_stale_const_alternatives` builds the whole-kernel model of a real emission after DCE (accepted) and with the dropped alternatives put back (refused). The zero exemption applies only when the zero VReg is reserved (`SsaCpsatHints::zero_reserved`, set by the pipeline, the per-section repair and the window probe); otherwise a missing 0 is refused like any other operand. The scheduler JSON's `const_alu_derivable` counts only alternatives the model can use (not the zero form). **Window probe:** the pruned window model (`restrict_to_window`) dropped the producer of a kept ConstChoice's ALU operand when that producer and its readers were far from the window (the alternative's read is not a `dep_ids` edge), so the new error fired (and before it, the alternative was silently unusable in the reduced model but usable in the full one). The producers of every kept ConstChoice's operands, and their latest readers, are now kept; test `pruned_window_keeps_const_choice_operand_producers`. This made the reduced model more constrained than the full one, so it does not explain the open "reduced model is not exact" entry on the `startup-window-probe` branch, where the reduced model is less constrained.

- [x] **Greedy with `valu_shift_fixed_to_none` could place a vector op without a vector slot** – Found in review of PR #73; pre-existing. `valu_shift_fixed_to_none` is set by the VALU-shift hint pass (`--valu-shift-hint-pass`, `--hint-passes`), not by `--valu-shift valu` (that passes an empty fixed shift set, which already forbids shifts). `can_shift` stayed true in `ssa_greedy::schedule_ssa_greedy_core`, so (1) on the normal path, with the six vector slots full, `try_place` returned `Shifted` (8 scalar slots taken) but the op was not recorded in `shifted_ops` and lowered as a seventh vector op; (2) on the force path, `SlotResult::NoRoom` arm, an op the policy would not shift was marked scheduled with no slot. **Fix:** `can_shift` is false when `valu_shift_fixed_to_none` (both paths); the force path takes its slot before anything else and, with none, puts the op back on the deferred list (it takes a later cycle) instead of marking it scheduled; every `Shifted` result is recorded unless the caller fixed the shift set. Only the first greedy run of a hint-pass build was affected: `ScheduleWithFixedChoices` always re-schedules with the shift set fixed, so no emitted kernel had an over-full cycle (the simulator asserts slot limits per bundle in any case), but the hint pass chose its shifts from a schedule that had used scalar slots for unrecorded shifts. Hint-pass builds therefore change (greedy 2r 193→200, 16r 2008→2091 cycles with `--valu-shift-hint-pass`); default builds are byte-identical. Tests: `test_valu_shift_fixed_to_none_keeps_vector_slot_limit` (normal path) and `..._when_force_scheduling` (a policy that never allows a shift, so only the `NoRoom` arm can overfill) in `ssa_greedy/tests.rs`; both failed with 7 vector ops in a cycle.

- [x] **CP-SAT scratch cumulative ignored same-cycle reuse** – Within a cycle, reads happen before writes, so a word last read at cycle C can take a value written at C. Address assignment and the greedy counter use this, but the CP-SAT cumulative counted each value over `[def, last_read + 1)`. At cycle C it therefore counted both the values dying at C and those born at C. This is not rare: it happens along every dependency chain. On scheduler JSONs from 2r, 4r and 16r greedy builds, `scripts/scratch_time_overcount.py` shows the per-cycle count over-stating the exact load by 46-68 words at the peak and by up to 80 words in a single cycle. The full-kernel solve and the per-section repair both searched a smaller space than the real budget allows. **Fix:** `--cpsat-scratch-time phase`, now the default, ends each value's interval at its last read, `[def, last_read)`. Its peak is exactly the allocator's per-cycle peak; proofs `A8-phase-interval-is-allocator-span` and `A8-phase-peak-exhaustive` in verification/allocation_conjectures.py. `--cpsat-scratch-time cycle` keeps the old count for ablation. Test: `test_ssa_cpsat_phase_scratch_allows_same_cycle_reuse` (at a 10-word budget, cycle is infeasible; phase is feasible and allocates).

- [x] **Per-section CP-SAT models were not reproducible (#54)** – `live_in_for_section_filtered` (`kernel_builder/round_budget.rs`) returned a section's live-in values in `HashMap` order. The per-section model creates one scratch interval per live-in value in that order, so two runs with the same options built different models and could return different schedules. Found by the segment-mode cell of `scripts/cpsat_model_identity.py` (`3x256`, `--scheduling-pressure-policy greedy`). **Fix:** the live-in list is sorted. Full-kernel models are unaffected.

- [x] **`test_deterministic_budget_reaches_the_solver_through_kwargs` ran close to the 120 s pytest timeout** – It built 4 rounds / batch 64 in-process (115 s alone under load; timed out inside the suite). **Fix:** build 2 rounds / batch 32 instead (about 8 s), the smallest size measured whose solve does not reach OPTIMAL within 0.5 deterministic time (2 rounds / batch 16 does), and assert from the solver log that the budget reached the solver parameters and that the solve ended Feasible, not OPTIMAL and not on the wall clock. The global 120 s limit is unchanged.

- [x] **Same-cycle scratch write conflict (shifted VALU adjacent intervals)** – Two shifted VALU destinations with intervals [22,23] and [23,24] both write lanes in cycle 23, but the allocator read the end of [22,23] as a last read and gave the second the same block; `verify_no_same_cycle_scratch_write_conflict` then rejected the kernel (3r/40, `--const-choice load`, tightening off). **Fix:** the allocator's value spans (`compute_value_spans`) extend to the write phase of a value's last write cycle (`last_write_cycles`: shifted destinations, vector groups), so a value still being written in its last cycle conflicts with any other writer of that cycle. ## Fixed (historical)

- [x] **Greedy / merged hint violates engine capacity (VALU, ALU)** – Fix: rebase all sections in `tick_tock_ssa/` so merged hint is strict concatenation. See below for details.

**Symptom (historical):** When building the CP-SAT model with greedy hints, you see warnings like:

```
  WARNING: VALU overflow at cycle 175: 7 > 6
  WARNING: ALU overflow at cycle 178: 16 > 12
  ...
  Note: Merged hint has engine capacity issues (VALU: N, ALU: M). CP-SAT will rebalance.
```

**Intent:** Sections are meant to be **concatenated** in time: section 0 at `[0, L0)`, section 1 at `[L0, L0+L1)`, section 2 at `[L0+L1, L0+L1+L2)`, etc. So the merged hint should never have two sections using the same cycle — we bump each section’s cycles by the sum of previous sections’ makespans.

**Cause (fixed):** Only sections that exceeded the scratch budget ran per-section CP-SAT and got their cycles written back as `section_offset + local_cycle`. Sections that stayed within budget were never rebased; they kept the initial greedy schedule’s cycles, which overlap with other sections (greedy schedules the whole kernel in one space). So the “merged” hint was a mix of concatenated sections and overlapping greedy cycles.

**Fix:** In `scheduler_rs/src/kernel_builder/tick_tock_ssa.rs`, at the **start** of each section’s iteration we **rebase** that section (whether we run per-section CP-SAT or not): set `op.cycle = section_offset + (op.cycle - min_c)` so the section occupies `[section_offset, section_offset + span)`. Then advance `section_offset` by that span. Rebase-at-start ensures `segment_hints` (e.g. `c - section_offset`) are in local cycle space when building the segment model. The merged schedule is thus a strict concatenation of sections.

**Verification:** We are allowed to exceed scratch in the greedy scheduler, but not slot constraints. If the merged hint ever has VALU/ALU capacity violations, `scheduler_rs/src/cpsat_scheduler.rs` panics (merge bug or single-section schedule exceeding capacity).

**Merged hint (cycles + choices):** The final full-kernel CP-SAT receives a single merged hint: for each section, either the greedy solution or the per-section CP-SAT solution. We maintain `current_select_fma` and `current_const_add_imm` (and cycles on `ssa_ops`): before running per-section CP-SAT for a section we pass the current merged choices for that section’s ops into the segment; after it runs we update cycles and those choice sets with the segment result. So the combination of greedy-or-CP-SAT per section is exactly what the final model is hinted with. See `scheduler_rs/src/kernel_builder/tick_tock_ssa.rs` (section loop and “Merged hint state” comment). Post-merge scratch peak uses `sections_exceeding_budget(..., Some(&section_select_fma_overrides))` so each section's peak reflects that section's FMA/vselect choices (greedy or per-section CP-SAT); see `round_budget.rs`.
