# Known bugs and limitations

## Open

- **`compute_live_intervals` gives an untouched vector group a [0, 1] interval** – A group none of whose VRegs is written by a scheduled op (its producer was a skipped dead store) still gets an 8-word interval at cycle 0 (`unwrap_or(0)` in the group pass of `address_assign.rs`). Kernels are DCE'd before scheduling, so this has only been seen on random test programs; the greedy agreement check filters such groups out. **Fix direction:** skip groups with no write and no read.

- **Greedy policy inputs still count freed words per operand** – `build_inflation_candidate` and the sort candidates compute `words_freed` and LUC from `srcs` only, so they miss `keep_live` and vector-group aliases and count `x + x` twice. The budget check and the counter itself are exact (T16); these are ordering heuristics only.

- **CP-SAT scratch model can undercount liveness (value's interval ends at one pre-chosen reader)** – In section 8b of `cpsat_scheduler/model.rs`, each value's live interval ends at the cycle of a single reader chosen before solving (`vreg_last_use`: the reader with the latest cycle in the greedy hint, or the highest index without hints). Nothing forces that reader to be the last one in the solution, and for a shifted reader the main cycle variable is used, not its lane cycles. If the solver moves another reader later, the model counts the value as dead while it is still live. The backstop is address assignment (budget exceeded after a "feasible" solve), so the effect is rejected solves, not wrong kernels. Confirmed by code reading; reproduced only on a toy replica (`docs/CPSAT_VARIABLE_MODELLING_REVIEW.md` section 6). **Fix direction:** interval end >= every reader's last read time.

- **T7 counterexample: slot tightening excludes a feasible schedule** – Theorem T7 in [docs/LIVENESS_SPECIFICATION.md](docs/LIVENESS_SPECIFICATION.md) claimed that slot-aware ASAP/ALAP tightening "only removes infeasible regions" so the tightened bounds still contain at least one feasible schedule. **Spec bug:** That claim is false for composition (multiple steps + precedence fixpoint); Z3 counterexample T7-two-step shows two valid one-step exclusions can remove all feasible schedules. **Behavioral bug:** 2r/16b with tightening → 368-cycle schedule (295 empty cycles); same config without tightening → 36-cycle **valid** schedule, so a feasible schedule exists but is excluded or the solver finds a bad one. **Z3 proof of error:** T7-strong-guarantee-fails-asap-only (`uv run python -m verification.verify -t T7-strong-guarantee-fails-asap-only`) returns **SAT**: there exists a feasible schedule (e.g. (0,1,2)) that the ASAP-only exclusions remove. So the SAT result **proves an over-tightening error** in ASAP/ALAP tightening (we exclude at least one feasible schedule; strong guarantee violated). **Z3:** One-step lemma proven; composition not; strong guarantee proven for entailed exclusions only; attempt for ASAP-only fails (result preserved). **Workaround:** Use `--no-enable-asap-alap-tightening`. **Fix direction:** Tightening or fixpoint logic must be changed so we still tighten beyond greedy but composition preserves at least one feasible schedule (greedy-cap would contradict the goal). See [docs/SLOT_TIGHTENING_T7_COUNTEREXAMPLE.md](docs/SLOT_TIGHTENING_T7_COUNTEREXAMPLE.md) § "What we actually need".

- **CP-SAT presolve INFEASIBLE on SelectChoice toy tests (no greedy hints)** – Seven tests in `cpsat_scheduler::tests::ssa_tests` fail with CP-SAT status INFEASIBLE during presolve: "empty domain after intersecting with [0]" on a cumulative constraint (Flow capacity 1 with optional intervals). **Root cause (found):** `enable_asap_alap_tightening: true` (default). Investigation test `test_investigate_valu_shift_toy_presolve_infeasible` shows that only the variant with `enable_asap_alap_tightening: false` passes; baseline, no default hint, default machine, and ForceFma all still fail. So ASAP/ALAP tightening over-constrains for these small programs and triggers presolve INFEASIBLE. **Workaround:** Use `enable_asap_alap_tightening: false` when running CP-SAT on small/toy models without greedy hints; or mark tests `#[ignore]`. See `docs/CP_SAT_PRESOLVE_INFEASIBLE_ANALYSIS.md`.

- **Validation failure: hash value used as offset in idx computation (kernel_to_validate.json, 4r/256)** – Traced with `scripts/debug_validation_trace.py` and `scripts/trace_group20.py`. All 256 batch indices wrong. **Cycle 985:** `vstore` writes final-round hash values to scratch 10–17 (group 0’s value output). **Cycle 986:** `multiply_add(49, 49, 27, 10)` computes `idx = idx*2 + offset`; the “offset” operand is read from scratch 10–17. Those locations were just overwritten at 985 with the **hash**, so the multiply_add uses the hash value as offset instead of the wrapped 0/1. Result: wrong indices (e.g. got 56 vs ref 27) and wrong values. **Likely cause:** Scratch allocation or scheduling reuses the same registers for (1) round output value and (2) offset input to next idx, and the store at 985 overwrites the offset before the multiply_add at 986 reads it (or the dependency graph allows the wrong ordering). **Repro:** Run validation on `kernel_to_validate.json` with `--rounds 4 --batch-size 256`; trace with `uv run python -m scripts.debug_validation_trace --kernel kernel_to_validate.json --rounds 4 --batch-size 256` and `uv run python -m scripts.trace_group20 --kernel kernel_to_validate.json --rounds 4 --batch-size 256 --group 0`. **Note:** Run trace scripts as `python -m scripts.<script>` from project root to avoid `scripts/bisect.py` shadowing stdlib `bisect`.  
  **Deep dive (root-cause hypothesis):** Two distinct VRegs—the **hash value** (produced by xor at 984, read by vstore at 985) and the **offset** (produced by `Sub(v_2, bit)`, read by the idx-update `multiply_add` at 986)—were assigned the **same scratch address** (10). Linear-scan in `address_assign.rs` reuses an address only when the previous VReg’s interval has ended. So one of these intervals was wrong: (1) the hash value’s interval end was &lt; 986 (value not extended to vstore’s cycle), or (2) the offset’s interval end was &lt; 984 (offset not extended to multiply_add’s cycle). Liveness is extended from each op’s `srcs` to that op’s cycle; vstore has `srcs = [addr, src]`, multiply_add has `srcs = [idx, v_2, offset]`. **Next steps:** Re-run with `SCHEDULER_DEBUG=1` and `--output-json`, inspect stderr for `[DEBUG compute_live_intervals]` vstore and confirm value VReg extended to vstore cycle; in scheduler JSON use `vreg_to_addr` to find VRegs at address 10 and check `vregs` intervals for overlap; add unit test: value at T, vstore at T+1, offset at T−1, multiply_add at T+2 → assert value and offset get different addresses.

## Fixed

- [x] **Greedy live-word counter disagreed with interval liveness** – The greedy now compares its counter with `address_assign::compute_live_intervals` after every run (spec T16) and fails on a difference. The first runs showed three disagreements in real kernels, all undercounts: `keep_live` values were released at their last operand read (256 words; 2-round peak reported 1016, real 1112; 4-round 1265 vs 1408); write groups were counted lane by lane instead of as an 8-word block (up to 28 words); `x + x` decremented x's reader count twice (1 word). The property test then showed two more on random programs: readers that are skipped dead stores kept their operands live forever, and `compute_live_intervals` ignored `keep_live` on a vector group or lane. **Fix:** counter rule in `docs/LIVENESS_SPECIFICATION.md` T16 (`count_written_dest`, `release_read_values` in `ssa_greedy/mod.rs`); group pass in `address_assign.rs` reads `keep_live`. Greedy cycles: 2r 193, 8r 1004, 16r 2007 unchanged; 4r 446 → 456 (the throttle now sees the real 1408). Tests: `test_liveness_agreement_*`.

- [x] **Greedy force-schedule dropped an op that had no free slot** – The force path took the best deferred op off the list and, if its engine was full this cycle, never put it back; the run ended with "Scheduling failed: only scheduled 16/21 ops". With a forced-shift op and a full ALU it also skipped the rest of the cycle's bookkeeping. Found by the liveness property test (budget 16). **Fix:** the op goes back with the other deferred ops. Test: `test_force_schedule_without_slot_keeps_op`.

- [x] **ALU direct capacity constraint wrong (300+ empty cycles)** – The entry described `12*makespan + 8*s >= alu_count + 8*shiftable_count`. The code has since been `12*makespan - 8*s >= alu_count` (`capacity_alu` in `cpsat_scheduler/model.rs`), which is the corrected form; the entry was stale. Confirmed while analysing the bound gap (`docs/BOUND_GAP_ANALYSIS.md` section 2).

- [x] **Forced encoding modes reported INFEASIBLE (`--valu-shift alu`, `--const-choice load`, 3r/40, 5r/16)** – CP-SAT bounds its search with the greedy schedule (horizon, ALAP = greedy cycle + 15, greedy-cap tightening, domain widening), which is only valid if the greedy used the encodings the model forces. The greedy ignored the forced modes, so under `--valu-shift alu` every domain was capped near a schedule that needs far fewer ALU slots, and presolve proved infeasibility. **Fix:** the greedy pass honours forced modes (`ForcedEncodings` in `pipeline/passes/greedy.rs`); the model checks `greedy_schedule_matches_forced_modes` and otherwise uses the greedy only as a hint, not as a bound; lane variables are hinted whenever the greedy matches. Tests: `tests/test_forced_modes.py`.

- [x] **CSE shared SUB read a SelectChoice-FMA operand one cycle early (`--select-choice fma`, 3r/64)** – The shared `true_val - false_val` SUB of a SelectChoice CSE group was only required to run at producer cycle + 1. When the operand is itself a SelectChoice lowered as FMA its result is visible at cycle + 2, so the SUB could read the address in the cycle the multiply_add writes it. **Found with:** `verification/kernel_dataflow.py` (first finding: `-` at cycle 69 reading an address that still held a constant). **Fix:** `select_fma_extra_delay` in `cpsat_scheduler/model.rs` is added to both `cse_sub_after_producer_*` constraints; new post-solve check `verify_cse_sub_precedence`. Regression test: `test_ssa_cpsat_cse_shared_sub_waits_for_selectchoice_fma_operand`.

- [x] **Shifted consumer of a SelectChoice FMA read its operand one cycle early (3r/batch 40-64, 4r/16, others)** – A select lowered as sub + multiply_add produces its result at cycle+2. The CP-SAT model added that delay to the consumer's main cycle variable but not to the eight per-lane cycle variables of a consumer shifted to scalar ALU, which only had cycle+1. One lane could then read the address before the multiply_add wrote it. This was the "3 rounds, batch ≥ 40, depth 3" failure (only one lane of one group wrong), and it also broke `--rounds 4 --batch-size 16` with default options and `--const-choice load` at 3r/40. **Found with:** `verification/kernel_dataflow.py` (first finding: scalar `^` at cycle 60 reading an intermediate hash stage). **Fix:** section 5d of `cpsat_scheduler/model.rs` applies the FMA delay to every lane; `verify_all_raw_precedence` now checks lane cycles of shifted consumers. Regression tests: `test_ssa_cpsat_shifted_consumer_of_selectchoice_fma_waits_two_cycles_per_lane`, `test_verify_all_raw_precedence_checks_shifted_consumer_lanes`.

- [x] **Per-section budget check ignored gap cycles** – After greedy we reported "peak_live=4552" but "CHECKING EACH ROUND" showed every section within budget. **Cause:** `sections_exceeding_budget` only sampled liveness at cycles where that section had an op, so gap cycles (between one section's last op and the next section's first op) were never sampled. **Fix:** Precompute per-section min/max op cycles; for each section sample from min_c through the gap to `min(next section's min_c - 1, max_c)` so liveness in gap cycles is included. `scheduler_rs/src/kernel_builder/round_budget.rs`.

- [x] **Segment scratch model missing live_out VRegs** – Per-section CP-SAT found a feasible solution within scratch budget, but post-merge check reported the same section exceeded budget (e.g., section 13: peak 1594 words vs budget 1536). **Root cause:** The segment scratch model in `cpsat_scheduler/` collected `live_vregs` by filtering `vreg_def_op.keys()` to only include VRegs that had a use *within the segment* (`vreg_last_use.contains_key(v)`). This excluded VRegs defined in the segment but only used *after* the segment (true `live_out` VRegs), causing the model to underestimate peak scratch. The post-merge check correctly included these VRegs, leading to a mismatch. **Fix:** After building scratch intervals for `live_vregs`, add missing `live_out` VRegs that are defined in the segment but not used within it. For each such VReg, add an interval `[def_cycle, segment_end+1)` to the scratch model. Also updated hint verification to include these VRegs. `scheduler_rs/src/cpsat_scheduler.rs` (lines ~3009-3030 for scratch model, ~3210-3224 for hint verification). Unit tests added in `round_budget.rs` to verify `sections_exceeding_budget` correctly counts live_out VRegs.

- [x] **CP-SAT loose makespan** – Makespan domain was forced to `[capacity_lower_bound, horizon]` with `capacity_lower_bound` inflated by `critical_path_len` (max ASAP + 1). That overestimates because the model uses variable-length steps (completion_cycle for shifted, +2 for SelectChoice FMA). Solver found 609 with 416 empty cycles; compaction reduced to 192. **Fix:** Pass 0 for the dependency floor when calling `compute_capacity_lower_bound_global` in the SSA path so `capacity_lower_bound` is the actual capacity-derived lower bound (min over x,y,z only). Precedence constraints in the model enforce any dependency lower bound. `scheduler_rs/src/cpsat_scheduler.rs`.

- [x] **Force-schedule VALU slot overflow (7 > 6)** – In the greedy scheduler's emergency force-schedule path (`ssa_greedy/mod.rs:836-845`), when VALU was full (6 ops) and the op was shiftable, `fits_slots` passed (shift possible), but `strategy.allow_shift()` returned false (pressure policy blocked shift). The `else` branch blindly did `valu_used += 1`, exceeding the 6-slot limit. This caused the CP-SAT per-section hint verification to panic: `"Merged hint violates engine capacity (VALU: 1 cycles)"`. Triggered in 4-round depth-3 section 3 where high liveness pressure activated the AdaptivePolicy's shift suppression during force-scheduling. **Fix:** Added intermediate guards — if VALU is full and strategy blocks the shift but ALU has room, force the shift anyway (force-schedule already ignores budget). Regression test: `test_force_schedule_never_exceeds_valu_capacity`.

- [x] **CP-SAT solution validation false VALU violation (7 > 6 at cycle N)** – Post-solution `validate_ssa_slot_limits` could report "CP-SAT solution violates VALU slot limit at cycle 96: 7 > 6" even when the model's cumulative constraint was satisfied. **Root cause:** For SelectChoice FMA (no-delta) ops in CSE groups, the model uses one shared SUB per group at `sub_cycle`, plus one FMA per consumer at `cycle+1`. Validation treated each consumer as contributing both sub at `cycle` and fma at `cycle+1`, over-counting the shared SUB by (N−1) for N consumers in a group. **Fix:** Made validation CSE-aware: `validate_ssa_slot_limits` and `try_validate_ssa_slot_limits` now accept `cse_group_results` and `op_idx_to_cse_group`. For CSE consumers, only the FMA at cycle+1 is counted; the shared SUB is counted once per active group at `sub_cycle`. `scheduler_rs/src/cpsat_scheduler/validation.rs`.

## Fixed (historical)

- [x] **Greedy / merged hint violates engine capacity (VALU, ALU)** – Fix: rebase all sections in `tick_tock_ssa/` so merged hint is strict concatenation. See below for details.

**Symptom (historical):** When building the CP-SAT model with greedy hints, you see warnings like:

```
  WARNING: VALU overflow at cycle 175: 7 > 6
  WARNING: ALU overflow at cycle 178: 16 > 12
  ...
  Note: Merged hint has engine capacity issues (VALU: N, ALU: M). CP-SAT will rebalance.
```

**Intent:** Sections are meant to be **concatenated** in time: section 0 at `[0, L0)`, section 1 at `[L0, L0+L1)`, section 2 at `[L0+L1, L0+L1+L2)`, etc. So the merged hint should never have two sections using the same cycle — we bump each section’s cycles by the sum of previous sections’ makespans.

**Cause (fixed):** Only sections that exceeded the scratch budget ran per-section CP-SAT and got their cycles written back as `section_offset + local_cycle`. Sections that stayed within budget were never rebased; they kept the initial greedy schedule’s cycles, which overlap with other sections (greedy schedules the whole kernel in one space). So the “merged” hint was a mix of concatenated sections and overlapping greedy cycles.

**Fix:** In `scheduler_rs/src/kernel_builder/tick_tock_ssa.rs`, at the **start** of each section’s iteration we **rebase** that section (whether we run per-section CP-SAT or not): set `op.cycle = section_offset + (op.cycle - min_c)` so the section occupies `[section_offset, section_offset + span)`. Then advance `section_offset` by that span. Rebase-at-start ensures `segment_hints` (e.g. `c - section_offset`) are in local cycle space when building the segment model. The merged schedule is thus a strict concatenation of sections.

**Verification:** We are allowed to exceed scratch in the greedy scheduler, but not slot constraints. If the merged hint ever has VALU/ALU capacity violations, `scheduler_rs/src/cpsat_scheduler.rs` panics (merge bug or single-section schedule exceeding capacity).

**Merged hint (cycles + choices):** The final full-kernel CP-SAT receives a single merged hint: for each section, either the greedy solution or the per-section CP-SAT solution. We maintain `current_select_fma` and `current_const_add_imm` (and cycles on `ssa_ops`): before running per-section CP-SAT for a section we pass the current merged choices for that section’s ops into the segment; after it runs we update cycles and those choice sets with the segment result. So the combination of greedy-or-CP-SAT per section is exactly what the final model is hinted with. See `scheduler_rs/src/kernel_builder/tick_tock_ssa.rs` (section loop and “Merged hint state” comment). Post-merge scratch peak uses `sections_exceeding_budget(..., Some(&section_select_fma_overrides))` so each section's peak reflects that section's FMA/vselect choices (greedy or per-section CP-SAT); see `round_budget.rs`.
