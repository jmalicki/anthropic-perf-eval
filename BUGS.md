# Known bugs and limitations

## Open

- **Validation failure (4 rounds, batch 8, tree-reduce depth 3)** – All 8 batch lanes wrong (value and some indices). **Trace (kernel_4r8b_depth3.json):** Cycle 786 vstore stores “value” from scratch 19 (written at 785 by xor). Round-3 expected hash 0x501b270f is **NOT FOUND** in scratch. Wrong index for batch 3 and 6 (17 vs 18, 23 vs 24) follows from wrong value: offset = 2 - (val&1), so wrong hash → wrong offset → wrong next_idx. **Hypothesis:** Same class as “hash value used as offset” below—scratch reuse or value extended to wrong cycle so we store an intermediate instead of the final hash, or the correct hash lives in a different register and was overwritten. **Scratch reuse fix applied:** Vstore value VReg extended to `op.cycle + 1` in `address_assign.rs`; VReg 213 at addr 19 has [784,786], no overlap. Schedule 788 vs kernel 790 cycles. Validation still fails (value in 213 is wrong); likely depth-3 computation bug. Depth 2 at 4 rounds passes; depth 3 fails. **Repro:** `uv run generate_ssa_kernel.py --rounds 4 --batch-size 8 --tree-reduce-max-depth 3 --validate --save-kernel kernel_4r8b_depth3.json`. **Trace:** `uv run python scripts/debug_validation_trace.py --kernel kernel_4r8b_depth3.json --rounds 4 --batch-size 8` and `uv run python scripts/trace_group20.py --kernel kernel_4r8b_depth3.json --rounds 4 --batch-size 8 --group 0`.

- **Validation failure: hash value used as offset in idx computation (kernel_to_validate.json, 4r/256)** – Traced with `scripts/debug_validation_trace.py` and `scripts/trace_group20.py`. All 256 batch indices wrong. **Cycle 985:** `vstore` writes final-round hash values to scratch 10–17 (group 0’s value output). **Cycle 986:** `multiply_add(49, 49, 27, 10)` computes `idx = idx*2 + offset`; the “offset” operand is read from scratch 10–17. Those locations were just overwritten at 985 with the **hash**, so the multiply_add uses the hash value as offset instead of the wrapped 0/1. Result: wrong indices (e.g. got 56 vs ref 27) and wrong values. **Likely cause:** Scratch allocation or scheduling reuses the same registers for (1) round output value and (2) offset input to next idx, and the store at 985 overwrites the offset before the multiply_add at 986 reads it (or the dependency graph allows the wrong ordering). **Repro:** Run validation on `kernel_to_validate.json` with `--rounds 4 --batch-size 256`; trace with `uv run python -m scripts.debug_validation_trace --kernel kernel_to_validate.json --rounds 4 --batch-size 256` and `uv run python -m scripts.trace_group20 --kernel kernel_to_validate.json --rounds 4 --batch-size 256 --group 0`. **Note:** Run trace scripts as `python -m scripts.<script>` from project root to avoid `scripts/bisect.py` shadowing stdlib `bisect`.  
  **Deep dive (root-cause hypothesis):** Two distinct VRegs—the **hash value** (produced by xor at 984, read by vstore at 985) and the **offset** (produced by `Sub(v_2, bit)`, read by the idx-update `multiply_add` at 986)—were assigned the **same scratch address** (10). Linear-scan in `address_assign.rs` reuses an address only when the previous VReg’s interval has ended. So one of these intervals was wrong: (1) the hash value’s interval end was &lt; 986 (value not extended to vstore’s cycle), or (2) the offset’s interval end was &lt; 984 (offset not extended to multiply_add’s cycle). Liveness is extended from each op’s `srcs` to that op’s cycle; vstore has `srcs = [addr, src]`, multiply_add has `srcs = [idx, v_2, offset]`. **Next steps:** Re-run with `SCHEDULER_DEBUG=1` and `--output-json`, inspect stderr for `[DEBUG compute_live_intervals]` vstore and confirm value VReg extended to vstore cycle; in scheduler JSON use `vreg_to_addr` to find VRegs at address 10 and check `vregs` intervals for overlap; add unit test: value at T, vstore at T+1, offset at T−1, multiply_add at T+2 → assert value and offset get different addresses.

- **Bisection: ForceAlu / ForceLoad lead to CP-SAT INFEASIBLE (5 rounds, batch 16)** – Running `bisect_cpsat_validation.py --rounds 5 --batch-size 16 --cpsat-time-limit 90` shows PASS only for `const=optimize` + `shift=valu`; all `--valu-shift alu` and all `--const-choice load` combos fail with CP-SAT reporting INFEASIBLE (no kernel produced). **Note:** Hints do not cause INFEASIBLE—the solver proves the *model* (constraints) has no solution. So the root cause is that the constraint model is unsatisfiable under these forced options: either we over-constrain (e.g. ForceAlu requires more ALU capacity per cycle than 12, or ForceLoad requires more Load capacity per cycle than 2), or there is a bug in how we build the model for ForceAlu/ForceLoad (e.g. wrong intervals, precedence, or cumulative construction). **Hint change (done, unrelated to feasibility):** We skip hinting completion_cycle/alu_cycle/shiftable_chosen_cycle when ForceAlu and cycle for ConstChoice when ForceLoad, so the solver is not given an inconsistent complete hint; it still reports INFEASIBLE because the model itself is unsat. **To fix:** Inspect why the model is unsat—e.g. ASAP/ALAP or cumulative constraints for ForceAlu (all shiftable → ALU) and ForceLoad (all ConstChoice → Load)—and either relax bounds, fix a bug in optional-interval or cumulative setup, or accept that some forced combinations are infeasible at this scale.

## Fixed

- [x] **Segment scratch model missing live_out VRegs** – Per-section CP-SAT found a feasible solution within scratch budget, but post-merge check reported the same section exceeded budget (e.g., section 13: peak 1594 words vs budget 1536). **Root cause:** The segment scratch model in `cpsat_scheduler/` collected `live_vregs` by filtering `vreg_def_op.keys()` to only include VRegs that had a use *within the segment* (`vreg_last_use.contains_key(v)`). This excluded VRegs defined in the segment but only used *after* the segment (true `live_out` VRegs), causing the model to underestimate peak scratch. The post-merge check correctly included these VRegs, leading to a mismatch. **Fix:** After building scratch intervals for `live_vregs`, add missing `live_out` VRegs that are defined in the segment but not used within it. For each such VReg, add an interval `[def_cycle, segment_end+1)` to the scratch model. Also updated hint verification to include these VRegs. `scheduler_rs/src/cpsat_scheduler.rs` (lines ~3009-3030 for scratch model, ~3210-3224 for hint verification). Unit tests added in `round_budget.rs` to verify `sections_exceeding_budget` correctly counts live_out VRegs.

- [x] **CP-SAT loose makespan** – Makespan domain was forced to `[capacity_lower_bound, horizon]` with `capacity_lower_bound` inflated by `critical_path_len` (max ASAP + 1). That overestimates because the model uses variable-length steps (completion_cycle for shifted, +2 for SelectChoice FMA). Solver found 609 with 416 empty cycles; compaction reduced to 192. **Fix:** Pass 0 for the dependency floor when calling `compute_capacity_lower_bound_global` in the SSA path so `capacity_lower_bound` is the actual capacity-derived lower bound (min over x,y,z only). Precedence constraints in the model enforce any dependency lower bound. `scheduler_rs/src/cpsat_scheduler.rs`.

- [x] **Force-schedule VALU slot overflow (7 > 6)** – In the greedy scheduler's emergency force-schedule path (`ssa_greedy/mod.rs:836-845`), when VALU was full (6 ops) and the op was shiftable, `fits_slots` passed (shift possible), but `strategy.allow_shift()` returned false (pressure policy blocked shift). The `else` branch blindly did `valu_used += 1`, exceeding the 6-slot limit. This caused the CP-SAT per-section hint verification to panic: `"Merged hint violates engine capacity (VALU: 1 cycles)"`. Triggered in 4-round depth-3 section 3 where high liveness pressure activated the AdaptivePolicy's shift suppression during force-scheduling. **Fix:** Added intermediate guards — if VALU is full and strategy blocks the shift but ALU has room, force the shift anyway (force-schedule already ignores budget). Regression test: `test_force_schedule_never_exceeds_valu_capacity`.

## Fixed (historical)

- [x] **Greedy / merged hint violates engine capacity (VALU, ALU)** – Fix: rebase all sections in `tick_tock_ssa/` so merged hint is strict concatenation. See below for details.

**Symptom (historical):** When building the CP-SAT model with greedy hints, you see warnings like:

```
  WARNING: VALU overflow at cycle 175: 7 > 6
  WARNING: ALU overflow at cycle 178: 16 > 12
  ...
  Note: Merged hint has engine capacity issues (VALU: N, ALU: M). CP-SAT will rebalance.
```

**Intent:** Sections are meant to be **concatenated** in time: section 0 at `[0, L0)`, section 1 at `[L0, L0+L1)`, section 2 at `[L0+L1, L0+L1+L2)`, etc. So the merged hint should never have two sections using the same cycle — we bump each section’s cycles by the sum of previous sections’ makespans.

**Cause (fixed):** Only sections that exceeded the scratch budget ran per-section CP-SAT and got their cycles written back as `section_offset + local_cycle`. Sections that stayed within budget were never rebased; they kept the initial greedy schedule’s cycles, which overlap with other sections (greedy schedules the whole kernel in one space). So the “merged” hint was a mix of concatenated sections and overlapping greedy cycles.

**Fix:** In `scheduler_rs/src/kernel_builder/tick_tock_ssa.rs`, at the **start** of each section’s iteration we **rebase** that section (whether we run per-section CP-SAT or not): set `op.cycle = section_offset + (op.cycle - min_c)` so the section occupies `[section_offset, section_offset + span)`. Then advance `section_offset` by that span. Rebase-at-start ensures `segment_hints` (e.g. `c - section_offset`) are in local cycle space when building the segment model. The merged schedule is thus a strict concatenation of sections.

**Verification:** We are allowed to exceed scratch in the greedy scheduler, but not slot constraints. If the merged hint ever has VALU/ALU capacity violations, `scheduler_rs/src/cpsat_scheduler.rs` panics (merge bug or single-section schedule exceeding capacity).

**Merged hint (cycles + choices):** The final full-kernel CP-SAT receives a single merged hint: for each section, either the greedy solution or the per-section CP-SAT solution. We maintain `current_select_fma` and `current_const_add_imm` (and cycles on `ssa_ops`): before running per-section CP-SAT for a section we pass the current merged choices for that section’s ops into the segment; after it runs we update cycles and those choice sets with the segment result. So the combination of greedy-or-CP-SAT per section is exactly what the final model is hinted with. See `scheduler_rs/src/kernel_builder/tick_tock_ssa.rs` (section loop and “Merged hint state” comment). Post-merge scratch peak uses `sections_exceeding_budget(..., Some(&section_select_fma_overrides))` so each section's peak reflects that section's FMA/vselect choices (greedy or per-section CP-SAT); see `round_budget.rs`.
